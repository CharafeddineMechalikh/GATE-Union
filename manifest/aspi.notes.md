## The four-condition design, in data terms

The brief and the abstract describe four conditions; the artifact is **eight conditions = 2 states × 4 delivery channels**, and the four is the channel axis inside one state. Critically, **the released rows store no condition at all** (0 fields matching `condition`/`variant`); the paper states conditions are "instantiated at evaluation time" by `src/aspi/eval/runner.py`:

| Condition | Built from |
| --- | --- |
| `exec_benign` | `original_prompt`, clean env |
| `exec_tool` | `original_prompt` + W wrapper injected into task-tool output |
| `exec_user` | `original_prompt` + raw `attacker_goal` |
| `exec_next_turn` | turn 2 = raw `attacker_goal` |
| `clarif_benign` | `base_prompt` answered with `benign_clarification_response` |
| `clarif_tool` | `base_prompt`, task tool replayed on W-injected env |
| `clarif_ask_user` | `base_prompt` answered with `benign_clarification_response` + W |
| `clarif_user` | the three stored `injected_clarification_response` (HR/GS/CP), score = max over operators |

W = AgentDojo `ImportantInstructionsAttack`, applied at run time. Arithmetic that is **not** in the artifact: 728 × 8 = 5,824 evaluation instances and 728 × 3 = 2,184 operator instances. The repo ships **no `results/` directory**, so no ASR, utility or compliance label is available offline at all.

## Interception-boundary verdict: ASPI measures behaviour, not calls

ASPI is a model-behaviour benchmark. Its ground truth is computed post-hoc from environment state after the agent acted (`security = attacker goal executed`) plus an LLM-judge trajectory label (`FULL_COMPLIANCE`, `PARTIAL_COMPLIANCE`, `ACKNOWLEDGED_REFUSED`, `IGNORED`, `UNCLEAR`). Neither is a per-case expected outcome and neither is an interception point. **So ASPI can only contribute cases whose injected instruction culminates in a concrete tool call — and for those, the call has to be synthesised by us from `attacker_goal`, which is authoring, not harmonising.**

That subset is real, and ASPI proves it: its own rule-based detector (`metrics.py: attack_attempted_rule`) recognises attacks by matching argument values against exactly eight tool families — `send_email`/`forward_email` vs recipient emails, `send_money`/`schedule_transaction` vs IBANs, `delete_file` vs file ids, `get_/post_/visit_webpage` vs URLs, Slack `send_direct_message`/`send_channel_message`/`invite_user_to_slack`, `update_password` unconditionally, `create_/update_calendar_event` vs attendee emails.

## Escalation band

ASPI is the only audited source that operationalises ambiguity as data: every row carries `missing_slot` (331 distinct), `expected_clarification_question`, `base_prompt` (one required slot deleted) and `benign_clarification_response`, and all seven QC checks are slot checks. That is exactly the predicate our ESCALATE band needs — a call proposed while a required argument is still missing.

**But its labels do not let us separate escalate from block.** There is no `expected_outcome`, no severity, no verdict and no shipped result file; the only label-shaped field is `expected_clarification_question`. The escalate/block split must be assigned by us under SPEC §8 and recorded as our judgement, not inherited from ASPI. Two further screen facts: the clarification half is **dynamically excluded at run time** (row dropped with reason `no_ask_user_tool_call` whenever the agent fails to call `ask_user`), so which rows even reach the ambiguous state is model-dependent and unknowable offline; and 262/728 rows have an empty `ground_truth_task_answer`, 2 have an empty `claims_list`.

## Role in the corpus

Ambiguity-conditioned **escalation substrate** plus benign clarification controls. Supply ceiling ≈ 35 attack templates and 161 fully expressible rows, pre-dedup. Never reported as 728 attacks. `cases_mapped`/`cases_dropped` are 0 here because this is an acquisition audit, not a normalisation pass; the numbers above are ceilings, not mapped counts.
